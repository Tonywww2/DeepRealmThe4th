# 星界躯体：Java 与 KubeJS 开发者指南

本指南对应当前源码。目标版本是 Forge 1.20.1 和 NeoForge 1.21.1；Curios 是必需依赖，KubeJS 是可选依赖。规则 API 位于 `com.tonywww.deeprealm4th.astral`，容器布局位于 `astral.container`，属性键位于 `astral.score`，物品基类位于 `item`；`platform` 负责双版本接口适配。

四个可直接改写的 Java／KubeJS 示例，以及物品类型 tag 的检测方式，见[开发者快速指南](星界饰品-开发者快速指南.md)。

共用物品 ID、逐格节点、大数分数、动态数据加工与效果唯一组见[宝石系统 API 扩展指南](星界宝石系统-API扩展开发者指南.md)。

## 结算频率与只读计算轮

服务端 `calculation.interval_ticks` 默认是 `5`，范围为 1–1200。设为 `1` 恢复每 tick 求值。装备与菜单预览分别调度，正常 20 TPS 下默认周期约 0.25 秒，短暂条件可能在两次求值之间消失。首次装备、换物或换槽、自有容器写入、显式 `AstralRuntime.invalidate(player[, container])` 会提前触发下一次更新。等待期间继续使用最后完整属性快照。`recalculate` 每次强制建立新计算轮，返回独立结果。外部直接修改 NBT／组件的值会在下个周期重新读取。

自有存储写入会增加弱引用物品 revision，装备集合中的任意绑定或内容变化会失效该玩家所有躯体，覆盖 PLAYER 效果组。会话以 Player 实例和世界实例区分，物品绑定使用弱引用。Curios 摘下／换类型的 hook 失效其他容器并沿用旧快照清理行为。同物品的 NBT 更新也会调用该 hook，因此跳过失效，以免自身摘要写入绕过降频。相同物品实例替换由 live binding 身份检查识别，重生或重连会建立新会话。

已审计的纯评分适配层可在 `FillerDefinition.builder()` 上显式调用 `.readOnlySnapshot()`。该定义承诺所有回调仅读取玩家、世界、配置、输入和共享值，并接受本轮开始时冻结的容器输入。此时内部可共享容器副本，公共 `container()`、`filler()`、`itemCopy()`、`instanceData()` 仍返回防御性副本。未选择此契约的旧回调继续在每个 context 创建时复制容器。bases/finals 保留各 context 创建时的可见结果集合。

启用契约后，context 提供 `memoGet(key)` / `memoPut(key, value)` 和 `roundMemoGet(key)` / `roundMemoPut(key, value)`。首次缺失返回 null，Rhino 接受普通 JS 对象作为 Java Object，无需 Supplier 适配。memo 的所有权属于引擎，计算结束 finally 清空，旧 context 在轮结束后访问 memo 会抛出异常。不同计算调用即使处于相同游戏 tick 也互相隔离。

阶段 memo 按容器身份与稳定视图区分，阶段依次为 resolve、intrinsic、effective、medal，PLAYER 组探测另用 group-resolve。reads 与 calculate 共用 effective metadata 视图，intrinsic 失败后的 effective 不与之前的视图混用。不得在阶段 memo 中保存正在增长的基础分、最终分、writer、inputs 或节点局部环境。整轮 memo 跨阶段共享，应仅存明确接受单次取样的只读玩家状态或纯数据。键使用带版本的命名空间。JS `Object.freeze` 不会冻结 Java NBT，若共享 DTO 带 Java 对象，适配层仍须审计全部消费者只读，或转换为深只读的 JS 数据。

可维护的最小适配示例见 `examples/astral-kubejs/startup_scripts/astral_round_memo.js`。本轮 SenDimsBanForges 桥接适配将元信息和惰性负载按 effective 阶段共享，状态按轮共享，几何按节点实际读取惰性构建。reads 不解码负载或读取玩家状态，普通 intrinsic 仅在需要时查询主世界时间。目录必须在桥接初始化前完成注册，后续目录扩展应调用 `A.rebuildAttributeNames()` 更新属性名目录。参数和解析对象只在本轮节点闭包中复用，所有评分消费者须保持只读。部署过渡时桥接检测新 builder/memo 方法并回退到原接口，更新模组后才启用轮共享和新调度。

KubeJS Rhino 2001 的 `createCompiler()` 直接创建解释器，CodeGenerator 生成解释器内部字节码。本轮通过减少脚本进入次数和环境重复构造优化。已有 Java 节点／ScoreRules API 可继续承载选定的热点规则。[Rhino 2001 Context 源码](https://github.com/KubeJS-Mods/Rhino/blob/2001/common/src/main/java/dev/latvian/mods/rhino/Context.java)

## 星浆入口与进阶工艺

拟态星浆的虚空入口读取服务端配置：Forge 1.20.1 为世界目录下的 `serverconfig/deeprealm_4th-server.toml`，NeoForge 1.21.1 为游戏目录下的 `config/deeprealm_4th-server.toml`。

```toml
[travel]
void_entry_dimensions = ["minecraft:the_end"]
```

列表填写维度 ID，例如加入附属维度时写成 `["minecraft:the_end", "addon:sky"]`；空列表禁用此入口。配置只限定**来源维度**，目的地始终是深境四层。生存玩家手持拟态星浆落到虚空阈值时消耗一份，传送失败则不消耗。该选项在 Forge 1.20.1 和 NeoForge 1.21.1 使用相同键名。

组合锻造和投影框架组合合成都是数据配方类型。附属 Java 模组可把 JSON 放进自己的数据包；KubeJS 可在 `kubejs/server_scripts/astral_recipes.js` 用 `event.custom` 注册。例如：

```js
// NeoForge 1.21.1：与原版有序合成结果相同，ItemStack 使用 id/count/components。
ServerEvents.recipes(event => {
  event.custom({
    type: 'deeprealm_4th:combination_forging',
    result: {id: 'addon:forged_star'},
    ingredients: [
      {stack: {id: 'addon:raw_star'}},
      {stack: {id: 'minecraft:amethyst_shard', count: 2}},
      {stack: {id: 'deeprealm_4th:star_slurry'}},
      {tag: 'deeprealm_4th:astral/gems', count: 1}
    ],
    clicks: 3, cooldown: 10, levels: 7,
    name_key: 'recipe.addon.forged_star'
  })
  event.custom({
    type: 'deeprealm_4th:projection_combining',
    result: {id: 'addon:stellar_token'},
    steps: [
      {stack: {id: 'addon:raw_star'}, direction: 'material_on_frame'},
      {stack: {id: 'minecraft:amethyst_shard'}, direction: 'frame_on_material'}
    ]
  })
})
```

两种工艺的 `result` 和精确原料均使用当前版本原生的 ItemStack 配方格式。上述示例适用于 NeoForge 1.21.1，堆栈可写 `id`、`count` 和 `components`，例如 `{id: 'addon:raw_star', components: {'minecraft:custom_data': {charged: true}}}`。Forge 1.20.1 的堆栈对象改用 `item`、`count` 和 `nbt`，例如 `{item: 'addon:raw_star', nbt: '{charged:1b}'}`；`result` 与每个 `stack` 都须按此替换。Forge 使用 `CraftingHelper.getItemStack`，NeoForge 使用有序合成同款 `ItemStack.STRICT_CODEC`。`count` 默认 1；组合锻造将其视为该格最低消耗量，投影组合每步固定消耗 1 件。精确原料按物品和完整 NBT／组件匹配；`tag` 原料按标签与数量匹配。变量数据可用 `data_predicate`、`exact_data:false` 与 `data_transform`。产物的数量和数据也会保留；投影步骤同样可用 `tag`。

将锻造皮革垫放在铁砧顶面，右键打开 4×3 持久输入格。组合锻造无序匹配，每条 `ingredients` 占一格并消耗其 `stack.count` 或标签原料的 `count`；同格可多放，不匹配的额外物品会阻止配方。原料使用 `stack` 或 `tag`，二者只选一个。`clicks` 默认 3，`cooldown` 默认 10 刻，`levels` 默认 0；完成最后一击时一次扣除等级，关闭界面重置点击进度。`name_key` 可省略，此时显示产物名称。输出进入背包，满时掉落。`material_on_frame` 是手持材料右键框架，`frame_on_material` 是手持框架右键材料，任意容器界面中可修改的格子均可操作。合成格中只有框架和一件材料时同样执行一步：材料在框架之前为 `frame_on_material`，之后为 `material_on_frame`，结果与叠放相同；带 `data_transform` 的配方需要能提供玩家的合成界面（原版工作台与物品栏）才能在合成格中完成。投影配方仍要求 2–9 条有序步骤。Java 附属也可在自身 `data/<namespace>/recipes/`（Forge）及 `data/<namespace>/recipe/`（NeoForge）目录提供同样内容。项目内置两类工艺配方由 `generateAstralProcessRecipes` 任务生成。

完整内置流程见[星界材料与工艺](星界材料与工艺.md)。

## 注册一件填充物

填充物按物品 ID 关联定义，因此既能使用附属模组新物品，也能使用已有物品。注册只做一次；物品必须真实存在，且不要注册为可装入自身的容器。

```java
AstralFillers.register("addon:orbit_gem", FillerDefinition.builder()
    .activation(FillerActivation.STACKABLE)
    .base(ScoreType.STRENGTH, 2)
    .bonus(ScoreRules.adjacent("addon:anchor_gem", ScoreType.STRENGTH, 3))
    .bonus((context, phaseScores, output) -> {
        if (context.player().getHealth() < 10) {
            output.add(ScoreType.CONSTITUTION, 1);
        }
    })
    .bonus((context, phaseScores, output) ->
        output.add(ScoreType.AGILITY, phaseScores.get(ScoreType.STRENGTH) * 0.5))
    .build());
```

此段是 **API 写法示例**，`addon:*` 物品与数值不是项目正式设定。`ScoreRules.adjacent` 只检查上下左右开放且有效的格子；至少一个指定物品相邻时加分一次。`FillerContext` 还提供 `x()`、`y()`、`itemAt(x,y)` 和 `count(itemId)`，便于附属写自己的组合条件。`itemAt` 和 `count` 都忽略关闭格、冲突失效和同 ID 唯一效果的后续副本；这些物品仍保存在容器中。

每件填充物可选择 `FillerActivation.UNIQUE_WORN`（同 ID 只允许放 1 件）、`STACKABLE`（多件各自结算）或 `UNIQUE_EFFECT`（多件可放但同 ID 只结算第一个开放格）。默认是 `STACKABLE`。`.suppressedBy("addon:anchor_gem")` 是有向冲突：指定物品出现在任一开放格时，本件保留在格子里但暂不结算，移除对方后自动恢复。冲突只影响结算，不改变物品存储；界面悬停会提示冲突或重复造成的暂不生效。

结算采用同一逐格节点引擎：解析各格、计算全部基础分、声明读取来源、按依赖结算最终分数、汇总后执行勋章。上述固定规则通过节点适配器执行：附加分读取本轮基础分，转换按格序读取已完成的修正结果；来源不足时缩小该条转换。Java 回调可读取玩家状态，但应避免修改玩家、容器或传入的物品栈；节点回调异常会回退到该格基础分并进入诊断结果。六分数自身不会改变任何 Minecraft 属性。

战士勋章作为内置示例注册为 `deeprealm_4th:warrior_medal`。先将最终力量分数 `s` 按最低 0 分处理，再使最终攻击力提升 `ln(1 + max(0,s)/15) × 100%`。`s=15` 时约为 +69.3%；任何负力量均按 0 分结算。疾行勋章按最终敏捷提供至多 +30% 移动速度，守御勋章按最终体质提供至多 +10 最大生命值。Java 附属可用 `.medal((context, scores, attributes) -> attributes.multiplyTotal(AstralAttributeIds.ATTACK_DAMAGE, fraction))` 定义最终值百分比修饰，`fraction=0.01` 表示 +1%；`attributes.add(...)` 是固定数值加算。`AstralAttributeIds` 还提供 `MOVEMENT_SPEED` 和 `MAX_HEALTH`。佩戴中的容器将服务器结算的分数及属性写入物品栈，供物品提示预览并通过 Curios 的 `getAttributeModifiers` 应用；分数改变时刷新，卸下饰品时清除快照并由 Curios 移除修饰。

内置六种基础晶石 `strength_gem`、`agility_gem`、`intelligence_gem`、`constitution_gem`、`perception_gem`、`magic_gem` 每件为对应分数 `+1`，生效类型均为 `STACKABLE`。`arid_ridge_gem`、`magma_vein_gem`、`canopy_gem`、`tidal_gem` 为 `UNIQUE_EFFECT`，各有一项基础分及两项相邻／数量组合规则，效果不取决于玩家当前所在的生态股。战士勋章也是 `UNIQUE_EFFECT`。精确数值见[星界躯体与填充物](星界躯体与填充物.md#内置晶石)。

二十九种晶石的自然获取通过 Forge／NeoForge 的全局战利品修饰器接入：只在 `deeprealm_4th:fourth_layer` 且战利品表为沙漠神殿、下界要塞、丛林神庙或沉船宝箱时追加物品。同一张原版战利品表在其他维度不会被本模组追加晶石。每个符合条件的宝箱有独立的 `1/3` 基础晶石、`1/9` 对应主题晶石和 `1/4` 扩展稀有池机会；具体来源见[宝箱获取](星界躯体与填充物.md#深境四层宝箱获取)。三枚勋章使用基础晶石、金锭、紫水晶碎片和对应器具通过工作台合成。

Java 附属可让物品继承 `AstralFillerItem`，构造时传入一个或多个完整翻译键；基类按顺序显示规则说明，并自动追加简短的生效类型及有向冲突提示。需要给分数着色时，可使用接收 `List<Component>` 的构造方法，并用 `AstralScoreColors.name(type)`、`gain(type, amount)` 或 `color(component, type)` 生成提示组件。六分数颜色集中在 `AstralScoreColors.rgb(type)`，容器分数面板、躯体预览和内置填充物提示共用；目前力量为红、敏捷为青绿、智力为蓝、体质为琥珀、感应为淡紫、魔力为洋红。动态数值可重写 `appendAstralTooltip`。容器物品提示预览非零分数与内置攻击力百分比；Curios 根据容器的属性方法显示属性加成；容器内悬停战士勋章还会显示当前分数对应的百分比。本模组专属创造模式物品栏自动收录 `deeprealm_4th` 命名空间内的注册物品；其他模组命名空间的附属物品应加入附属自己的物品栏。当前正式物品各有独立的 16×16 透明贴图。

分数允许小数。分数转换可通过 `.conversion((context, currentScores, output) -> { ... })` 声明来源扣减和目标增加，扣减超过当前可用来源分数时整条规则按可用比例缩小。KubeJS 的 `AstralRules.convert(source, target, fraction, targetMultiplier)` 是便捷写法：扣除当前来源的指定比例，再将扣除量乘以倍率加到目标。

Java 也可使用 `ScoreRules.when(predicate, target, amount)`、`ScoreRules.perScore(source, target, multiplier)`、`ScoreRules.countAtLeast(itemId, minimum, target, amount)`、`ScoreRules.convert(source, target, fraction, targetMultiplier)`、`ScoreRules.attributePerScore(source, attributeId, multiplier)` 和 `ScoreRules.attributeMultiplyTotalPerScore(source, attributeId, fractionPerPoint)`。还提供 `percentOf(source,target,rate,cap)`、`percentWhenAdjacent(...)`、`percentWhenCountAtLeast(...)`、`whenExperienceLevelAbove(...)`、`whenHealthAbove(...)`、`whenHealthAtMost(...)`、`whenFoodAtLeast(...)` 和 `whenNightVision(...)`。比例使用基础阶段分数，先将负来源当作 0，再应用单件上限；`rate=0.25` 表示 25%。条件阈值的严格／包含关系由方法名确定。KubeJS 的 `AstralRules` 提供同义工厂，以及 `warriorMedal()`。`when` 的条件可读取 `FillerContext.player()`、`itemAt(x,y)` 和 `count(itemId)`；规则回调应保持只读。

## 基础容器的网格尺寸

`base_container.width` 与 `base_container.height` 控制内置星界躯体的实际网格外框，范围均为 1–64；默认 12×9、中心 6×5 开放。`layout` 的行数必须等于 `height`，每行长度必须等于 `width`。例如 4×5 全开放容器：

```toml
[base_container]
width = 4
height = 5
layout = ["XXXX", "XXXX", "XXXX", "XXXX", "XXXX"]
```

Forge 容器存储对以下整合包缩框场景提供只读重排：`deeprealm_4th:base_container` 的原108格存储裁去左4、上2格后映射到4×5；`kubejs:astral_rune` 的原64格存储裁去左1、上1格后映射到6×6。预览和结算不修改原 NBT，下一次存取时写入新格子编号。裁框以外的已有物品优先移入空格，装不下的保留在 `AstralContainer.Overflow`，后续空格出现时再取回，避免缩小尺寸导致物品丢失。

## 继承容器物品

继承 `AstralContainerItem` 即可沿用物品栈存储、打开菜单、分数预览和 Curios 装备钩子。重写 `layout(ItemStack)` 提供不同尺寸；重写 `mayInsert(AstralInventory, int, ItemStack)` 时先调用 `super.mayInsert(...)`，再叠加限制。

```java
public final class SmallAstralBody extends AstralContainerItem {
    public SmallAstralBody(Properties properties) {
        super(properties);
    }

    @Override
    public ContainerLayout layout(ItemStack stack) {
        return ContainerLayout.parse(8, 6, List.of(
            "........", ".XXXXXX.", ".XXXXXX.",
            ".XXXXXX.", ".XXXXXX.", "........"));
    }
}
```

菜单根据布局尺寸和 `X`/`.` mask 生成格子。大于基础 12×9 的尺寸虽然在解析层允许，界面可能缩得难以操作，附属应在目标分辨率下检查可用性。物品栈不应堆叠；基类已将最大堆叠数设为 1。

附属容器要进入本模组专属的 Curios 槽，必须符合 `curios:base_container` item tag 的槽位匹配规则。槽位守卫还会确认物品确实继承 `AstralContainerItem`。

专属槽的空槽图标由 `data/deeprealm_4th/curios/slots/base_container.json` 指向 `deeprealm_4th:slot/base_container`；资源为 `assets/deeprealm_4th/textures/slot/base_container.png`，采用 16×16 透明像素画。

## KubeJS

安装与游戏版本匹配的 KubeJS 后，在 `kubejs/startup_scripts/` 中使用 `AstralFillers`、`FillerDefinition`、`ScoreType` 和 `AstralRules` 绑定。可运行示例见 [KubeJS 示例](../examples/astral-kubejs/README.md)，覆盖固定规则和共用 ID 的动态节点。修改启动脚本后重启游戏；同一物品 ID 在一次启动中只能注册一次。`AstralItemData`、`GemPayload` 与 `AstralNumber` 可在服务器脚本使用，`AstralRuntime` 仅在服务器脚本开放。未安装 KubeJS 时，Java 内容仍可使用。

宝石承载星体力量、星座决定组合规则是项目设定。以上 `addon:*` 示例只验证 API，不构成正式的宝石、星体或星座对应关系。
