# 主干—支流水系：第一轮原型

本文是 V1 历史实验记录，不代表当前安装包状态。当前 `0.1.8` 的海洋、干旱台地与真实群系模组兼容测试见 [V5 工作记录](海洋与干旱山地-V5计划与验证.md)；`0.1.7` 的边缘自然化、性能及自然河水更新见 [V4 工作记录](边缘自然化与生成性能-V4计划.md)，水系接入见 [V3 记录](全局水系接入-V3工作记录.md)。下文保留原型当时的失败诊断，不追改为通过。

实施依据：[已确认的重构计划](主干支流水系与群系气候-重构计划.md)。本轮只实施基础拆分、群系气候适配与离线排水实验，不替换正式生成器。

开发版本为 `0.1.6-prototype`；它不是已经装上新河流的发行版。原有 0.1.5 安装包和存档保留。

后续：`0.1.6-prototype2` 的自然山体和非圆润岸线实验见 [V2 记录](自然地形与非圆润河道-V2原型.md)。本文保留 V1 的实验结果与失败诊断；V2 也尚未解决正式接入门槛。

## 已实现的代码路径

1. `BaseTerrain` 保存原有无河流地形公式。`TerrainProfile` 调用它、叠加旧河流，再通过共同的收尾逻辑产生正式列；没有复制两份会逐渐分歧的高度函数。
2. `BaseBiomeResolver` 统一群系池、根 tag 额外群系和稳定选择。`baseBiomeAt` 只读 H0，`biomeAt` 仍读正式最终地形；前者不可能经由河流覆盖反向递归。
3. `BiomeClimateAdapter` 在服务器初始化完成后读取 `getModifiedClimateSettings()`，保留温度、downfall、降水开关和温度修饰器。实际冷暖判定使用原生 `coldEnoughToSnow`，不冒充调用不存在的跨版本公开位置温度 getter。
4. `ClimateSnapshot` 导出不可变、顺序稳定的气候及已解析群系池。离线算法不依赖 Minecraft 类、不内置“名字对应温度”表，且可以用不同种子复用同一注册表快照。
5. `DrainageGraph` 在有限域抖动三角网上做盆地候选识别、Priority-Flood、排水 DAG、汇水面积、有效来水和沿程损失累计，并计算 Strahler 河级及流量相关宽度。非平坦段选取最陡的合法下降边，平坦段保持洪泛顺序打破平局。每条网格边逐格检查真实陆地遮罩，排除只在两个端点合法却横穿虚空的连接。图中只为满足流量阈值的河段绘水。
6. `verifyHydrologyPrototype` 检查数据并直接绘制完整河网、温度/降水/径流、斜视地形/纵剖面和分区失败诊断。

依赖严格单向：H0 → 基础群系 → 注册表气候 → 排水图。排水图当前没有任何正式区块生成入口。

## 供水约定

Minecraft 温度不是摄氏度，downfall 不是毫米降水。本轮采用可复现的长期均值近似：

```text
P = hasPrecipitation ? clamp(downfall, 0, 1) : 0
E = clamp(0.10 + 0.16 × temperature, 0, 0.65)
R = max(0, 0.88 × P - E)
Qout = max(0, ΣQupstream + R × area - reachLoss)
```

气候采用中心权重 1/2、四向 48 格邻点各 1/8 的有限混合，作用于水文供水，不修改游戏群系。冷地区仍可贡献长期径流；没有新增季节、融雪或动态天气。

供水使用群系基础温度；温度修饰器保存在快照中，但还没有把其位置噪声模拟进长期蒸发。最终水面是否冻结必须在阶段 3 使用实际位置与最终群系的原生判定，不能用这张混合温度图代替。当前验证使用默认维度参数和默认群系池；第三方新增群系/修改器的专门装包测试、冷山与冻河候选尚未完成。

干旱股的默认基础群系无降水，且与湿润股隔着虚空，因此预期没有密集常年水源。旧 `river` 群系不再反向为基础地形供水。需要常年沙漠大河时应另行设计同股湿润源区，而非伪造降水。

- `01-完整水系.png`：湿润地形、远端山地、干旱地形；源头、汇口和终点候选均显示。
- `02-群系气候.png`：基础温度、供给、有效径流对照。没有擅自增加冷山或冻河群系。
- `03-地形与纵剖面.png`：H0 斜视及最大主干的原地面/分析水位。竖向有标明的放大，不是游戏截图。

橙圈仅为地形低洼终点候选，不代表已经验证可持续湖泊；淡蓝积水也是分析结果，不能直接填进世界。红叉是无合适内部盆地时的诊断终点，绝非获准的虚空瀑布或海洋出口。显示的折线仍是排水拓扑，不是完成的细化曲流与自然河岸。

## 不能接入正式生成的原因

**当前父域分区没有通过无限世界连续性验收。** 子区可以共享同一父图的完整河段 ID、交点、水位、流量和方向，因此逆序、并发、丢弃后重建可以一致；但两个独立父域尚未共享上游汇水范围，边界的水量/水位可以不同。测试主动保留这一反例，不将“裁切同一张图”说成“解决了无限世界”。

有限域边界目前是未知外部条件，而不是默认出水口。Priority-Flood 的填洼高度只是分析排水势，不拿来填平地形。较深积水候选还缺湖泊收支、溢口及开山限值审核。因此，即使图的局部水量守恒，也不能直接将蓝线转成方块水。

下一轮应继续阶段 2 的全局宏观排水骨架和父域入口/出口契约，然后再做走廊内曲线细化、深洼拒绝/重选路与湖泊平衡。上述技术门槛及样品确认均通过后，才能实施阶段 3 的河岸和方块水。不能跳过门槛发布。

## 第一轮离线实测

两端各通过 455,548 次局部水系断言。三种种子、三种区域共九组排水图在 Java 17/21 上的指纹逐组相同。流量减半供水测试不改排水拓扑且不增加下游水量；逐点汇口收支、全域收支、汇水面积、拓扑无环、下游水位不升高和不穿越虚空检查通过。

种子 42：

| 区域 | 有水节点 | 源头 | 汇口 | 最高 Strahler 级 | 最大分析积水深度 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 湿润温带/丛林 | 629 | 61 | 47 | 4 | 29 |
| 远端山地 | 588 | 67 | 49 | 3 | 38 |
| 干旱股 | 0 | 0 | 0 | 0 | 16（仅排水势，不绘成水） |

同一父图的中线有 8 条真实跨子区河段；两份独立重建父图的契约逐项相同。并发、逆序和无缓存重建通过。

两个相邻独立父域实测 **55 个公共边界节点水位/水量不一致**，因此 `INTEGRATION_GATE=FAIL`。原型任务的成功退出表示局部性质和这个已知失败诊断都被复现，并非发布验收成功。最大 38 格的分析积水同样不符合可直接实装的要求。

本机单个 2048 格/32 格间距域求解约 0.35–0.47 秒，属于离线测量，包含基础地形和气候采样；未测正式区块吞吐、峰值内存或全局宏观骨架成本，不能用此数值承诺游戏性能。

旧地形两端各通过 3,219,574 次基础断言；299,568 列冻结几何指纹为 `9e13290f425a4d0e`，陆地和中心指纹分别仍为 `e044a615cb00990c`、`aced97098c2b22a8`。这些是对未改变正式生成行为的回归证明，不是新水系实装证明。
