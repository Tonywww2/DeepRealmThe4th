# 星界躯体：饰品系统设计

状态：设计与原型实现记录。本文区分已确认需求、当前实现和待确认设定；两个版本已经通过编译与资源处理，仍需游戏内交互验证。

## 已确认的玩法

- 项目同时支持 Minecraft 1.20.1／Forge 和 1.21.1／NeoForge，饰品基于 Curios。
- 核心物品是 `deeprealm_4th:base_container`，显示名“星界躯体”。容器数据跟随**物品栈**，不是跟随玩家。
- 在物品栏中直接右键星界躯体，或者手持直接使用，打开同一容器。打开容器不要求它已装备。
- 容器布局来自配置文件中的 12 列、9 行矩阵。`X` 表示开放。默认开放区为居中的 6×5：从 1 开始数第 4～9 列、第 3～7 行。
- 每件填充物占 1 格；格内最多放 1 件。只有饰品装备在 Curios 槽位时，内部填充物才参与结算。
- 六项分数是力量、敏捷、智力、体质、感应、魔力。分数自身不改变玩家属性。
- 普通填充物可给固定分数、条件分数、按另一项分数给分数，或把一项分数转成另一项。
- 普通填充物可检查上下左右的相邻开放格：若至少一个相邻格是指定填充物 A，则额外获得指定分数。多个 A 默认只触发一次；斜对角不算相邻。
- 每种填充物定义一种生效类型：唯一佩戴（同 ID 只能放 1 件）、可叠加（多件都生效）、唯一效果（可放多件但同 ID 只生效 1 件）。还可定义有向冲突：开放格中存在 A 时 B 保留但不生效，A 移除后 B 恢复。
- 职业勋章读取结算后的分数，产生属性加成，归属到容器饰品。首个样例“战士勋章”按最终力量 `s` 使最终攻击力提升 `ln(1 + max(0,s)/15) × 100%`。
- Java 附属可继承基础容器类，制作不同尺寸和特性的容器；Java 与 KubeJS 作者都能定义填充物。

## 系统边界

Curios 负责装备槽和佩戴生命周期；本模组负责容器内部格子、持久化、菜单和分数结算。容器内部格子不是 108 个 Curios 槽。不能把 Anatomy 的实体附件直接移植：那会让多件容器共用一份内容，也会在物品转移后丢失对应关系。Anatomy 的布局数据和菜单适配方式可以参考，但它的 `X` 是锁格，本项目语义相反。

建议的分层如下：

| 层 | 责任 | 扩展点 |
| --- | --- | --- |
| 容器定义 | 宽、高、可用格、放置校验、特殊规则 | 可继承的 `AstralContainerItem` 与布局提供器 |
| 物品栈存储 | 以固定槽位索引保存内容，跨存档和同步 | 版本化读写接口 |
| 填充物定义 | 基础分与附加规则 | `FillerDefinition`／效果接口和注册器 |
| 结算器 | 从基础分到最终分，再读取勋章 | 可审计的阶段、上下文和结果对象 |
| Curios 桥接 | 装备时应用、卸下时移除属性 | 双加载器适配 |
| KubeJS 桥接 | 脚本注册填充物及规则 | 可选插件、脚本示例和类型提示 |
| 界面 | 12×9 格子、玩家背包、六分数、错误提示 | 基于定义的尺寸布局 |

## 物品栈容器与配置

基础容器的矩阵固定 12×9，按从上到下、从左到右读取。每行必须恰好 12 个字符，共 9 行；`X` 开放、`.` 关闭。配置错误应在启动时给出行号和期望长度，不使用半截布局继续加载。扩展容器可以覆盖尺寸与布局；配置项不能以基础容器的 12×9 约束误伤扩展容器。

默认矩阵：

```text
............
............
...XXXXXX...
...XXXXXX...
...XXXXXX...
...XXXXXX...
...XXXXXX...
............
............
```

当前按固定索引 `y * width + x` 将内容保存到容器物品栈。配置关闭已有物品所在格时，物品留在该格但不生效；再次开放后恢复可见和可用。关闭格中的物品仍显示、可取回，悬停时有提示。Forge 1.20.1 使用带版本号和槽位索引的 NBT；NeoForge 1.21.1 使用物品栈的原版容器组件。今后若允许已有附属容器改变尺寸，还需单独设计迁移规则，避免原尺寸之外的内容丢失。基础容器最大堆叠数为 1。

服务端是格子和分数的权威。客户端只发“打开”“点击格子”等操作请求；服务端检查当前被操作的物品仍是同一件、玩家仍持有它、格子开放、物品符合填充物定义，并同步结果。打开菜单时须给正在编辑的物品建立稳定定位；从背包移走该物品或交换装备时应关闭菜单，避免写入另一件外观相同的饰品。禁止把容器放入自身或形成嵌套循环。

12×9 格子加玩家背包超过常规容器高度，建议界面让星图格子区独立滚动或分页，分数与玩家背包保持可见；具体视觉方案可在功能实现时验证屏幕缩放和点击命中。

## 分数与勋章

分数结果使用以六个固定键为主的不可变快照，同时保留每项来源明细，供界面解释。所有数值在服务端计算。非有限数值、溢出、脚本异常、负数规则及小数精度要在公开 API 中明确处理；不能让脚本回调破坏整件物品的加载。

建议结算器接收容器内容、玩家上下文与注册定义，并产出：

1. 六项最终分数；
2. 每件填充物对每项分数的贡献；
3. 职业勋章生成的属性修饰；
4. 失败或未生效规则的可诊断信息。

结算阶段固定为“基础分 → 条件/比例加分 → 分数转换 → 勋章”。附加分规则读取阶段开始时的统一快照；转换按格子顺序执行，每条读取前一条转换后的剩余分数。分数允许小数；转换扣除来源，再按规则给定倍率增加目标，来源不足时按可用量缩小本条结果。勋章只读取最终分数；基础六分数不直接映射任何原版属性。战士勋章按最终力量 `s` 使最终攻击力提升 `ln(1 + max(0,s)/15) × 100%`，其中 `s=15` 时约为 +69.3%，所有负力量均先按 0 分计算。该修饰由容器装备时的 Curios 钩子施加；卸下、换槽、移走勋章或改动填充物后移除旧值并应用新值。同 ID 战士勋章属于“唯一效果”，多件可保存但只结算第一个开放格中的一件。

效果按格子从上到下、每行从左到右执行；附加分阶段共享同一分数快照，转换阶段逐条读取前一条执行后的结果。当前属性桥接每 5 tick 回查装备和动态条件，仅在属性值变化时更新修饰。属性修饰 ID 保持稳定，避免重新装备时累计或误删其他模组修饰。

## 扩展 API 草案

Java 面向附属作者的最小契约：

```java
public class CustomAstralBody extends AstralContainerItem {
    public CustomAstralBody(Properties properties) {
        super(properties);
    }

    @Override
    public ContainerLayout layout(ItemStack stack) {
        return ContainerLayout.parse(8, 6, List.of(
                "........", ".XXXXXX.", ".XXXXXX.",
                ".XXXXXX.", ".XXXXXX.", "........"));
    }
}
```

以上展示当前基类的扩展方式。附属通过重写 `layout` 改尺寸和矩阵，通过 `mayInsert` 叠加放置规则；打开菜单、容器持久化和同步由基类及公共层负责，不要求附属复制完整屏幕或网络代码。附属物品仍需按两个版本的 Curios 标签规则加入专属槽。

填充物不应靠中央 `switch(itemId)` 判断。建议以稳定 ID 注册 `FillerDefinition`，包含可放入条件、基础分、零到多个效果、可选职业勋章效果；规则接口接收只读的玩家/容器/当前分数上下文和一个受控结果写入器。Java 作者可以实现接口或使用构建器。注册时验证 ID、数值及所引用的分数键。

相邻规则由 `ScoreRules.adjacent("mod:item_a", ScoreType.STRENGTH, amount)` 提供 Java 便捷入口；KubeJS 入口为 `AstralRules.whenAdjacent(...)`。两者读取相同的开放格布局，不要求附属作者自己计算一维槽位索引。

通过 `FillerDefinition.builder().activation(FillerActivation.UNIQUE_WORN)` 等调用选定复制规则；三个枚举值是 `UNIQUE_WORN`、`STACKABLE`、`UNIQUE_EFFECT`，默认 `STACKABLE`。通过 `.suppressedBy("mod:item_a")` 声明“存在 A 时本填充物不生效”。战士勋章为 `UNIQUE_EFFECT`，力量晶石为 `STACKABLE`。冲突与唯一效果只影响结算，不删除格子内物品。

KubeJS 应提供启动脚本可用的注册入口和服务端规则回调，并给出至少四种可复制示例：固定加分、条件加分、按分数加分、分数转换。脚本只声明规则，实际结算和属性应用仍由模组服务端完成。KubeJS 为可选依赖；未安装时 Java 定义与基础玩法正常运行。插件类、事件/binding 和脚本目录需分别核对两个游戏版本的 KubeJS API 后确定，不把仅适用于一个版本的示例称作通用示例。

## 内容与设定

宝石、星体和星座是本系统的**基础设定**：宝石承载星体力量，星座决定组合规则。普通填充物及其关系应服从这个定义。具体宝石和星体如何对应、哪些格子或物品构成星座、星座如何改变分数仍待定义；不能以美术偏好代替规则。容器贴图采用简单且易辨认的形式。术语、提示文案和中英文对照遵循 [饰品系统文案指南](饰品系统文案指南.md)。

最小可玩内容包括星界躯体、战士勋章和力量晶石。力量晶石每件提供 +1 力量分数，可叠加；战士勋章为唯一效果，按最终力量的对数公式提供百分比攻击力。首版通过创造模式物品栏或 `/give` 获取，具体星体力量的对应关系仍待确认。

## 验收点

- 两个版本分别启动，Curios、KubeJS 缺席/存在的预定组合按依赖策略正常处理。
- 两种打开方式指向同一件物品栈；背包中的多件容器内容不会串联。装备前后容器可编辑，只有装备时结算有效。
- 矩阵严格是 12×9，`X`/`.` 语义一致，格内最多 1 件，锁格不能放入。不同尺寸的附属容器不会被基础尺寸限制。
- 重登、转移、掉落、复制及配置变更不会造成物品丢失或复制；服务端拒绝伪造的点击和过期菜单请求。
- 六分数本身不改属性；战士勋章的最终攻击力百分比修饰在装备、卸下和改动填充物后准确更新，不累计残留。
- Java 和 KubeJS 示例能够注册新填充物；错误脚本有可定位日志，且不破坏原有容器数据。
