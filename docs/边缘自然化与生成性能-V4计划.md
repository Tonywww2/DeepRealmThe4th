# 边缘自然化与生成性能：V4 工作计划

目标：继续保留 0.1.6 已认可的主干—支流和整体漩涡，在不制造内部裂隙、单格尖刺和随机群系噪点的前提下，减少地形/群系边界的平滑轮廓；用实测数据优化生成开销。

## 顺序与验收

1. **先记录基线。** 固定种子、群系气候快照、坐标、遍历顺序、预热和重复次数；分别测无河流 H0、完整列冷缓存、重复访问及并发列请求。记录稳定结果指纹与 JFR 采样，不用含图片渲染的总耗时冒充区块生成耗时。
2. **先做保形优化。** 根据采样处理重复 H0/群系计算、内流湖距离计算、河段重复几何计算、缓存命中时的锁开销。缓存必须有界、属于生成器实例；不缓存全局世界状态，不降低采样精度。版本 3 的固定样本指纹必须与优化前一致。
3. **再做外观调整。** 保留大尺度群系斑块，在十几至几十格尺度加入有空间关联的边界扰动；陆地只在狭窄外缘增加侵蚀缺口，不重新引入内部裂隙。山体侧翼/山脚适度不规则，避免用每格白噪声堆“破碎感”。中心断崖、陆地比例、低径向增幅、三格海岸保护保持既定约束。改变外观的路径单独标识为生成版本 4，版本 3 仍可读取。
4. **比较与实服验证。** 同坐标绘制新旧地形/群系边缘；检查局部坡度、群系邻接连续性、边界细节、主支流连通和封水。重跑相同基准，分别报告保形优化与最终 V4 的成本，说明无法优化的部分；双端新测试世界检查生成、流水和原生生态入口。

## 当前代码中的待测候选

- `BaseTerrain.shape` 为自然地形仍先计算旧高度公式；同一 H0 又被排水、湖盆、气候和最终列反复查询。
- `LakeMask` 的每个距离网格点都对边界点反复执行 `hypot`。
- `WatershedRivers.sample` 每列请求都进入共享 tile 锁，且重复计算河段长度/投影常量。
- 群系竞争以平滑噪声为主，细尺度扰动偏弱；外缘主要由连续宽尺度场控制。

以上是候选，不是已经测得的热点或性能收益。以剖析和前后同工作负载结果决定保留哪些优化。

保留 0.1.6 安装包与 V9 测试世界；本轮不修改玩家旧区块。不升级加载器/Gradle，不引入新的噪声或性能依赖库。

## 补充：自然河水更新

定位到 `SpiralChunkGenerator.generateTerrain` 只调用 `ChunkAccess.setBlockState`，未安排流体后处理；这个生成阶段不会触发水方块的 `onPlace`。此前 `HydrologyVerification.prepare` 主动安排 tick 和邻居更新，只证明了激活后的封水，不足以证明自然生成会自行流动。

- 新生成的版本 3/4 主干支流和内流湖水体，使用原版含水层同样的 `markPosForPostprocessing` 入口，等区块及邻区就绪后由原版流体逻辑处理；不扫描整个世界，不持续重刷流体。
- 验收命令移除手动 tick/邻居更新，改用全新 V10 世界；检查自然产生的非源水、干列漏水以及保存重启后的状态。
- 已保存区块不会重跑生成后处理。提供管理员显式命令 `/fourthlayer updatewater [chunkRadius]`，默认周围 3×3、最大 5×5 区块，仅处理已加载、模型范围内的现有河水，不放置方块、不强制加载。执行后水会按原版规则变化，建议先备份旧存档。
- 平坦封闭河段由连续水源组成，正常更新后仍可能静止；本轮修复漏更新，不把所有水源强制改成“永远向下游流”的自定义流体。

实现与验证结果追加于下方；旧 V3 报告保留其历史含义。

## 已实现的优化

初始 JFR 采样确认热点包括湖盆边界距离、反复 H0 查询和河网 tile 锁。保形路径没有减少采样精度：

1. `LakeMask` 预先计算固定网格的 `hypot(dx,dz)*4` 表，保持原先浮点值，替换湖岸距离内循环。
2. `BaseTerrain` 在生成器实例内每线程缓存 8,192 个 H0 shape/column；`BiomeClimate` 每线程缓存 128 个资源键盐值及最近一个气候点。不缓存可变注册表或服务器对象。
3. `WatershedRivers` 将河段向量、长度与保守包围盒预计算进不可变 tile；每线程最近 tile 命中不再争用共享锁。缓存清理的 epoch 使线程局部旧 tile 失效。
4. V4 完成自然地形过渡的区域直接计算自然地形，跳过已经完全混出结果的旧山体公式。V3 仍保留原有计算顺序，以保证旧输出逐位一致。

新增缓存是有界内存换计算；没有宣称峰值堆内存下降。生成后的原版流体处理属于正确性修复，其运行开销不包含在纯算法基准中。

## 已实现的边缘细节

- 群系竞争共享 47/17 格尺度、18/5 格幅度的坐标扰动；保留原有大斑块，没有按单方块白噪声随机换群系。
- 陆地只在原边距小于 40 格的外带侧蚀，43/15 格尺度控制缺口；原边距至少 40 格的内部不改陆地遮罩。距中心 200～296 格渐入，避免制造一个新的硬半径边界。
- 山脊两翼宽度以 83/29 格尺度小幅变化，增加 13 格尺度、1.5 格幅度的地表起伏；不放大远端角度扰动，不引入尖峰地形。

- 每端旧地形 3,219,574 项、V3 水系 580,741 项、V4 水系 574,533 项、边缘/海岸 2,428,748 项断言通过。

- 对 V4 新遮罩补测海洋护岸：三种种子分别 8,037 / 5,781 / 7,774 个海洋水列，逐一检查周围包含斜角的三格范围，均由同水位水体或足高陆地封住；不是仅靠旧算法的护岸回归。
- 内陆实际高度单格四邻差在本轮网格上最大为 2，V3/V4 相同；中心半径 80 格内几何检查一致。它们是有界抽样，不是全世界形式化证明。
- 768 格群系对照区域中，V4 四格采样孤立单元 15/24,210，未形成散点噪声；相邻异类边总数 6,907（V3 为 6,618）。外缘面积不同，此项只作局部描述，不单凭该数字认定观感更好。
- 双端三张 V4 样品逐字节一致；两张 V3 样品与优化前 SHA-256 一致。0.1.6 两个安装包的校验值仍与 V3 记录一致。
- 新 JAR 默认生成版本为 4，缺省字段仍解码为旧版本 1，版本 3 继续可用。没有删除、重绘 V9 或玩家存档。

## 性能对照结果

2026-09-26 同机顺序运行，无本项目构建/测试服同时执行：每个加载器两轮独立 JVM，每轮依次运行未修改的 0.1.6 JAR、保形 V3、最终 V4；每次预热至少 4 秒、测量 5 次。`-Xmx1G`，全程启用同样 JFR profile。种子 42，四个 128×128 区域，按 16×16 区块顺序遍历共 65,536 列；气候来自真实双端快照。下表为每场景 10 次测量的中位数，单位毫秒：

| JVM / 场景 | 0.1.6 | 保形优化 V3 | 最终 V4 | V4 耗时降低 |
| --- | ---: | ---: | ---: | ---: |
| Forge Java 17 / H0 | 126.19 | 125.69 | 118.17 | 6.35% |
| Forge / 完整列冷生成 | 591.18 | 445.97 | 400.09 | 32.32% |
| Forge / 重复大区域 | 190.15 | 163.83 | 159.00 | 16.39% |
| Forge / 4 线程冷生成 | 460.91 | 328.33 | 288.67 | 37.37% |
| NeoForge Java 21 / H0 | 104.78 | 104.52 | 97.84 | 6.62% |
| NeoForge / 完整列冷生成 | 480.09 | 405.29 | 356.20 | 25.81% |
| NeoForge / 重复大区域 | 166.24 | 141.74 | 135.62 | 18.42% |
| NeoForge / 4 线程冷生成 | 372.10 | 291.59 | 259.15 | 30.36% |

不改变 V3 输出的部分单独贡献了约 24.56% / 15.58% 的冷生成耗时降低。H0 保形路径只有约 0.3% 的变化，视为没有明显收益；不是所有路径都被缓存加速。重复区域大于缓存，不能称为“全命中缓存吞吐”。并发包含四个工作线程的创建/等待时间；不能据此宣称相同倍率的全服并行加速。

同版本全部循环的指纹一致，保形前后逐位相同：H0 `f0ad2c591d8670c5`，最终列 `20b541bcc3777b8e`，并发汇总 `e18dab0e82df2704`。V4 外观本就改变，单独为 `3f9d96754c65b8a5` / `ad231ba19d67fb48` / `f1ad159f12fc0bf6`，两个 JVM 相同。

临时分配存在取舍：完整冷列的主线程平均分配，Java 17 为 149.00 → 138.13（保形 V3）→ 156.91 MiB（V4），最终比基线增加约 5.3%；Java 21 为 120.70 → 114.12 → 105.12 MiB。这里是执行期间累计分配，不是保留内存/堆峰值；并发线程分配未统计。缓存、细节计算与 JVM 逃逸分析影响不同，不能笼统宣传“更省内存”。

原始每次计时、范围、分配、指纹和 JFR 均保留于 `build/reports/terrain-performance/{forge,neoforge}/paired-*`，汇总为 `paired-summary.tsv`。最初短预热的 `v3-baseline/v3-optimized` 只是定位热点的初测，不与此表混算。完整区块的结构、地物、光照、流体 tick、存盘和客户端 FPS **尚未做前后配对性能测试**。

后续性能方向：优化后的 JFR 中 `LakeMask.create` 仍是明显热点，首次构建完整流域时仍存在 tile/model 锁竞争。当前只减少缓存命中的锁开销，并没有把冷流域构建改成并行；若继续改动，应单独设计去重构建与精确距离变换并重跑输出指纹，不能直接删除同步或近似湖岸距离。

## 实服验收（V10，seed=42）

Forge 47.4.0 / MC 1.20.1 已通过：实际气候输入 21,609 列、24 基础列及 24 海岸墙、29 个实际群系与 87 个保存的 quart 样本、64 列隔离低温输入。自然世界的冻河仍是条件未观测项，外扩搜索中低温候选 4,999、低温湿列 0，不把隔离输入当作实际冻河证据。

自然河水探针为内流湖 `(5171,-3888)`、汇口 `(5096,-3859)`、落差河段 `(5121,-4059)`，共 1,875 列、1,364 湿列。**测试安排的流体 tick 为 0，也没有邻居更新或手工放水。** 新区块生成后初查有 46 个非源水方块；经过正常游戏 tick 后 5,022 个水方块、101 个非源水，干列外泄 0；保存停服再启动后同样为 5,022 / 101 / 0。已释放本次新增的 27 个强加载区块并正常保存停服。

Forge 原生地物验证检出水草、树叶/树干、菌类及矿物，`failedFeatureIds=[]`；在 13 类生态地点调用原生生物生成规则，陆地、水生、下界及敌对类别均检出真实生成实体。不保证每个候选地点都生成生物，也不是长期自然生成调度器/生物上限性能测试。沙漠神殿、丛林神庙和平原村庄的自然结构、实际方块及战利品检查通过，没有执行 `/place`。

第一次批量命令末尾的 Check 因仅经过 13 个游戏 tick 被正确拒绝；大量验证命令占用主线程，墙钟经过几十秒不代表已经推进 200 游戏 tick。等待正常 tick 后再次检查为 1,046 tick，通过；重启后为 1,871 tick，通过。失败与成功报告均保留，不删除早期记录。
